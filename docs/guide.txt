1. WHAT IS THE INCEPTION PROJECT?
================================================================================

Inception is a system administration project at 42 School. The goal is to set
up a small but complete web infrastructure entirely inside Docker containers,
coordinated with Docker Compose, and running inside a Virtual Machine.

The stack you must build is:

    [Browser] --HTTPS--> [NGINX container] --FastCGI--> [WordPress container]
                                                              |
                                                        [MariaDB container]

In plain words: a user opens a browser, types your domain (login.42.fr), and
reaches a working WordPress site — secured with TLS, backed by a real MySQL-
compatible database, with all data persisted in volumes.

Key skills tested:
  - Understanding of Docker and container concepts
  - Writing Dockerfiles from scratch (no pre-built images allowed)
  - Orchestrating services with Docker Compose
  - Configuring NGINX, PHP-FPM, and MariaDB
  - Understanding of TLS/SSL certificates
  - Environment variable management and security
  - Volume and network design

2. CORE CONCEPT: CONTAINERIZATION VS VIRTUALIZATION
================================================================================

Virtual Machine (VM):
  - Emulates an entire computer, including hardware
  - Has its own full OS (kernel + userland)
  - Heavy: typically hundreds of MB to several GB
  - Slow to start (boots an OS)
  - Strong isolation (separate kernel)

Container:
  - Shares the host OS kernel
  - Packages only the application + its dependencies
  - Lightweight: typically megabytes
  - Fast to start (milliseconds to seconds)
  - Isolated via Linux namespaces and cgroups, but NOT as strong as a VM

Why containers for Inception?
  Each service (NGINX, WordPress, MariaDB) runs in its own isolated environment.
  They share the host Linux kernel but cannot interfere with each other's files
  or processes directly. Docker handles the isolation.

Linux primitives behind containers:
  - namespaces: isolate PID, network, mount, UTS, IPC, user namespaces
  - cgroups (control groups): limit and measure CPU, memory, I/O per process
  - Union filesystem (OverlayFS): layers images on top of each other efficiently

3. DOCKER — DEEP DIVE
================================================================================

--------------------------------------------------------------------------------
3.1 WHAT IS DOCKER?
--------------------------------------------------------------------------------

Docker is a platform that allows you to build, ship, and run applications in
containers. It provides:
  - A runtime to create and manage containers
  - A build system (Dockerfile -> image)
  - A registry (Docker Hub) to share images
  - A CLI to interact with all of the above

Docker uses a client-server architecture:
  - dockerd: the Docker daemon (server), manages everything
  - docker CLI: the client you type commands into
  - They communicate over a Unix socket (/var/run/docker.sock) or TCP

--------------------------------------------------------------------------------
3.2 DOCKER IMAGES
--------------------------------------------------------------------------------

An image is a read-only template used to create containers. Think of it as a
snapshot of a filesystem + metadata (what command to run, what port to expose,
etc).

Images are layered. Each instruction in a Dockerfile creates a new layer. Layers
are cached, so if you change only the last line of a Dockerfile, only that layer
is rebuilt.

Base images used in Inception:
  - Alpine Linux (lightweight, ~5MB)
  - Debian (penultimate stable version, e.g. Debian Bookworm)
  The project requires using the PENULTIMATE stable version of Alpine or Debian
  as the base, NOT the latest tag. Check what that is at evaluation time.

Important: you may NOT pull pre-built images for NGINX, WordPress, or MariaDB
from Docker Hub. You must build them yourself from Alpine or Debian.

--------------------------------------------------------------------------------
3.3 DOCKERFILES
--------------------------------------------------------------------------------

A Dockerfile is a text file with instructions to build an image. Each line is
an instruction and creates a layer.

Common instructions:

  FROM <image>:<tag>
    Sets the base image. Must be the first instruction.
    Example: FROM debian:bookworm

  RUN <command>
    Executes a shell command during the build phase.
    Example: RUN apt-get update && apt-get install -y nginx

  COPY <src> <dest>
    Copies files from the build context (your machine) into the image.
    Example: COPY conf/nginx.conf /etc/nginx/nginx.conf

  ADD <src> <dest>
    Like COPY but also handles URLs and auto-extracts tar archives.
    Prefer COPY unless you need ADD's extra features.

  ENV <key>=<value>
    Sets an environment variable inside the image.

  ARG <name>
    Defines a build-time variable (passed with --build-arg or in compose).

  EXPOSE <port>
    Documents which port the container listens on. Does NOT actually publish it.

  CMD ["executable", "arg1", "arg2"]
    The default command to run when a container starts. Can be overridden.
    Use exec form (JSON array), not shell form, to make the process PID 1.

  ENTRYPOINT ["executable"]
    Like CMD but harder to override. Often used for init scripts.
    If both ENTRYPOINT and CMD are set, CMD becomes the default arguments.

  WORKDIR /path
    Sets the working directory for subsequent RUN, COPY, CMD instructions.

  USER <username>
    Switches to a non-root user for subsequent instructions and at runtime.

Best practices for Inception Dockerfiles:
  - Combine RUN commands with && to reduce layers and image size
  - Clean package manager caches in the same RUN step:
      RUN apt-get update && apt-get install -y nginx && rm -rf /var/lib/apt/lists/*
  - Use COPY, not ADD, unless you need tar extraction
  - Always use exec form for CMD: CMD ["nginx", "-g", "daemon off;"]

Example — minimal NGINX Dockerfile:

  FROM debian:bookworm
  RUN apt-get update && apt-get install -y nginx openssl \
      && rm -rf /var/lib/apt/lists/*
  COPY conf/nginx.conf /etc/nginx/nginx.conf
  EXPOSE 443
  CMD ["nginx", "-g", "daemon off;"]

--------------------------------------------------------------------------------
3.4 DOCKER CONTAINERS
--------------------------------------------------------------------------------

A container is a running instance of an image. It is:
  - Ephemeral by default: when stopped and removed, any data written INSIDE it
    is lost (unless stored in a volume).
  - Isolated: its processes, filesystem, and network are separated from others.
  - Identified by a name or ID.

Container lifecycle:
  created -> running -> paused/stopped -> removed

Useful commands:
  docker ps           : lists running containers
  docker ps -a        : lists all containers (including stopped)
  docker inspect <id> : dumps full JSON info about a container
  docker logs <id>    : shows stdout/stderr of the container's main process
  docker exec -it <id> bash : opens an interactive shell inside a running container

--------------------------------------------------------------------------------
3.5 DOCKER VOLUMES
--------------------------------------------------------------------------------

Volumes are the mechanism for persisting data beyond the lifecycle of a container.
Without volumes, all data inside a container is lost when it is removed.

In Inception you need TWO volumes:
  1. WordPress database volume (for MariaDB data at /var/lib/mysql)
  2. WordPress files volume (for WordPress PHP files at /var/www/html)

Both volumes must be available on the host at: /home/login/data/

Types of Docker storage:
  - Named volumes:    managed by Docker, stored under /var/lib/docker/volumes/
  - Bind mounts:      a specific host directory is mounted into the container
  - tmpfs mounts:     stored in host memory only, not persisted

For Inception, bind mounts to /home/login/data/ are typically used so the
evaluator can inspect the data directly on the host machine.

Declaring volumes in docker-compose.yml:

  volumes:
    db-volume:
      driver: local
      driver_opts:
        type: none
        o: bind
        device: /home/${USER}/data/mariadb

    wp-volume:
      driver: local
      driver_opts:
        type: none
        o: bind
        device: /home/${USER}/data/wordpress

--------------------------------------------------------------------------------
3.6 DOCKER NETWORKS
--------------------------------------------------------------------------------

By default, containers on the same Compose project can reach each other by
service name (DNS resolution). However, you must define an explicit network in
Inception — you cannot use the default bridge network.

A user-defined bridge network allows containers to:
  - Reach each other by service name (e.g., wordpress can connect to mariadb)
  - Be isolated from other containers not on the same network
  - Have DNS resolution managed by Docker's embedded DNS

Declaring a network in docker-compose.yml:

  networks:
    inception:
      driver: bridge

Each service then joins the network:

  services:
    nginx:
      networks:
        - inception

Important rules from the subject:
  - You must NOT use --link (deprecated)
  - You must NOT use host networking mode
  - You must NOT use the default network
  - NGINX is the only container that should have its port (443) published to the
    host machine

--------------------------------------------------------------------------------
3.7 KEY DOCKER COMMANDS
--------------------------------------------------------------------------------

Build an image:
  docker build -t myimage:tag .

Run a container:
  docker run -d --name mycontainer -p 443:443 myimage:tag

Stop / start / remove:
  docker stop mycontainer
  docker start mycontainer
  docker rm mycontainer

Remove an image:
  docker rmi myimage:tag

Remove everything (containers, images, volumes, networks):
  docker system prune -a --volumes

List images / volumes / networks:
  docker images
  docker volume ls
  docker network ls

Inspect a container's IP or config:
  docker inspect mycontainer

Execute a command in a running container:
  docker exec -it mycontainer bash

View real-time logs:
  docker logs -f mycontainer

4. DOCKER COMPOSE
================================================================================

--------------------------------------------------------------------------------
4.1 WHAT IS DOCKER COMPOSE?
--------------------------------------------------------------------------------

Docker Compose is a tool for defining and running multi-container applications.
You describe all your services, networks, and volumes in a single YAML file
(docker-compose.yml), and Compose handles the orchestration.

Benefits:
  - One file to define the entire infrastructure
  - Start everything with one command: docker compose up
  - Services can depend on each other (depends_on)
  - Environment variables, volumes, and networks are declared declaratively

--------------------------------------------------------------------------------
4.2 THE docker-compose.yml FILE
--------------------------------------------------------------------------------

Structure:

  services:            # Each service = one container
    nginx:
      ...
    wordpress:
      ...
    mariadb:
      ...

  volumes:             # Named volumes used by services
    db-volume:
    wp-volume:

  networks:            # Networks connecting services
    inception:
      driver: bridge

Full annotated service example (NGINX):

  services:
    nginx:
      container_name: nginx            # Name of the running container
      build:
        context: .                     # Build context (directory with Dockerfile)
        dockerfile: requirements/nginx/Dockerfile
      image: nginx                     # Name to tag the built image
      depends_on:
        - wordpress                    # Start only after wordpress starts
      ports:
        - "443:443"                    # host_port:container_port
      volumes:
        - wp-volume:/var/www/html      # Mount the shared WordPress files
      networks:
        - inception
      restart: always                  # Restart policy
      env_file:
        - .env                         # Load environment variables from file

Restart policies:
  no           : never restart (default)
  always       : always restart (even on docker stop)
  on-failure   : restart only if the process exits with a non-zero code
  unless-stopped: restart unless explicitly stopped by the user

In Inception, "unless-stopped" or "always" is commonly used for all services.

depends_on:
  Compose will start the dependency first, but it does NOT wait for it to be
  "ready" (e.g., MariaDB fully initialized). For that, use healthchecks or
  a shell script with retries in your entrypoint.

env_file vs environment:
  env_file: loads variables from a file (good for secrets)
  environment: inlines variables directly in the compose file (bad for secrets)

ARG vs ENV:
  ARG is a build-time variable passed to docker build. Not available at runtime.
  ENV is a runtime variable, available inside the container when it runs.
  You can pass ARG values from compose using the "args:" key under "build:".

--------------------------------------------------------------------------------
4.3 KEY docker-compose COMMANDS
--------------------------------------------------------------------------------

Build and start in detached mode:
  docker compose -f srcs/docker-compose.yml up -d --build

Stop and remove containers (keeps volumes):
  docker compose -f srcs/docker-compose.yml down

Stop and remove containers AND volumes:
  docker compose -f srcs/docker-compose.yml down -v

View logs for all services:
  docker compose logs -f

View logs for one service:
  docker compose logs -f nginx

Rebuild a single service:
  docker compose build nginx

5. THE THREE MANDATORY SERVICES
================================================================================

--------------------------------------------------------------------------------
5.1 NGINX (with TLS)
--------------------------------------------------------------------------------

NGINX is a high-performance web server and reverse proxy. In Inception, it is
the ONLY entry point into the infrastructure. All traffic comes in on port 443
(HTTPS/TLS) and NGINX routes PHP requests to WordPress via FastCGI.

Key responsibilities:
  - Terminate TLS (decrypt HTTPS traffic)
  - Serve static files directly
  - Forward PHP requests to WordPress (port 9000, FastCGI protocol)

Requirements from the subject:
  - Must use TLSv1.2 OR TLSv1.3 ONLY (no older versions)
  - Port 443 only (HTTP/port 80 is not required and should be avoided)

Minimal nginx.conf for Inception:

  server {
      listen 443 ssl;
      server_name login.42.fr;

      ssl_certificate     /etc/nginx/ssl/login.42.fr.crt;
      ssl_certificate_key /etc/nginx/ssl/login.42.fr.key;
      ssl_protocols       TLSv1.2 TLSv1.3;

      root  /var/www/html;
      index index.php index.html;

      location / {
          try_files $uri $uri/ /index.php?$args;
      }

      location ~ \.php$ {
          fastcgi_split_path_info ^(.+\.php)(/.+)$;
          fastcgi_pass   wordpress:9000;
          fastcgi_index  index.php;
          include        fastcgi_params;
          fastcgi_param  SCRIPT_FILENAME $document_root$fastcgi_script_name;
      }
  }

How NGINX finds WordPress:
  Docker's internal DNS resolves "wordpress" to the IP of the wordpress container.
  NGINX sends PHP requests there on port 9000 using the FastCGI protocol.

The WordPress files volume (/var/www/html) must be mounted in BOTH the NGINX
container AND the WordPress container so NGINX can serve static assets and
WordPress can manage its PHP files.

--------------------------------------------------------------------------------
5.2 WORDPRESS + PHP-FPM
--------------------------------------------------------------------------------

WordPress is the CMS (Content Management System). PHP-FPM is the PHP runtime
that executes WordPress's PHP code. They run together in one container but
NGINX does NOT run in this container.

PHP-FPM (FastCGI Process Manager):
  - Listens on port 9000 (TCP) inside the container
  - Receives requests from NGINX via the FastCGI protocol
  - Executes PHP scripts and returns HTML to NGINX

WordPress setup in the container typically involves:
  1. Install PHP, php-fpm, and required PHP extensions (mysqli, curl, etc.)
  2. Download WordPress (wp-cli is the recommended tool)
  3. Configure wp-config.php with database credentials
  4. Run wp-cli to:
       - Install WordPress (wp core install)
       - Create the admin user
       - Create a second regular user (subject requirement)
  5. Start php-fpm in the foreground

WP-CLI (WordPress Command Line Interface):
  WP-CLI is a command-line tool for managing WordPress installations without
  using the web interface. Key commands:

    wp core download --path=/var/www/html
    wp config create --dbname=... --dbuser=... --dbpass=... --dbhost=mariadb
    wp core install --url=login.42.fr --title="My Site" \
        --admin_user=admin --admin_password=secret --admin_email=a@b.com
    wp user create user1 user@example.com --role=author --user_pass=pass

  Important: WP-CLI must be run as the www-data user, not root. Use:
    su -s /bin/bash www-data -c "wp ..."
  Or set the --allow-root flag (not recommended for production).

PHP-FPM configuration:
  The php-fpm pool listens on 0.0.0.0:9000 or a Unix socket.
  For Inception, TCP port 9000 is standard.
  Edit /etc/php/8.x/fpm/pool.d/www.conf:
    listen = 0.0.0.0:9000

Subject requirement: the WordPress container must have TWO users:
  1. An administrator (but the admin username must NOT contain "admin" or
     "administrator" — the evaluator checks this)
  2. A regular (non-admin) user

--------------------------------------------------------------------------------
5.3 MARIADB
--------------------------------------------------------------------------------

MariaDB is an open-source relational database, fully compatible with MySQL.
WordPress stores all its data here: posts, users, settings, comments, etc.

Typical setup in the container entrypoint script:
  1. Initialize the data directory if it doesn't exist:
       mysql_install_db --user=mysql --datadir=/var/lib/mysql
  2. Start MariaDB temporarily (without networking) to run SQL setup:
       mysqld --user=mysql --bootstrap < /tmp/init.sql
  3. The init SQL must:
       CREATE DATABASE IF NOT EXISTS <dbname>;
       CREATE USER IF NOT EXISTS '<dbuser>'@'%' IDENTIFIED BY '<password>';
       GRANT ALL PRIVILEGES ON <dbname>.* TO '<dbuser>'@'%';
       FLUSH PRIVILEGES;
  4. Start MariaDB normally (foreground process):
       exec mysqld --user=mysql

Why bootstrap? Because you need to create the database and user before WordPress
can connect, but you can't run SQL commands without a running server. The
bootstrap mode lets you pipe SQL to mysqld without starting the network listener.

The data directory (/var/lib/mysql) must be mounted to a volume for persistence.
If no volume is mounted, the database is wiped every time the container restarts.

MariaDB only exposes port 3306 internally (expose, not ports), so the WordPress
container can reach it by service name on that port, but the host machine cannot
directly connect to MariaDB — this is correct and expected.

6. TLS — TRANSPORT LAYER SECURITY
================================================================================

TLS is the protocol that encrypts communication between a browser and a server.
HTTPS = HTTP over TLS. TLS replaced SSL (Secure Sockets Layer).

TLS versions:
  SSL 3.0, TLS 1.0, TLS 1.1 : DEPRECATED and insecure
  TLS 1.2                    : Secure, widely supported (MUST support)
  TLS 1.3                    : Latest, faster handshake, more secure

Inception requirement: support TLSv1.2 and/or TLSv1.3 ONLY.

Certificates:
  A TLS certificate contains the server's public key and identity information,
  signed by a Certificate Authority (CA). For development/local projects like
  Inception, you generate a SELF-SIGNED certificate.

Generating a self-signed certificate with openssl:

  openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
    -keyout login.42.fr.key \
    -out login.42.fr.crt \
    -subj "/C=BR/ST=SP/L=SP/O=42/CN=login.42.fr"

  Flags:
    -x509        : output a self-signed certificate (not a CSR)
    -nodes       : do not encrypt the private key (no passphrase)
    -days 365    : validity period
    -newkey rsa:2048 : generate a new 2048-bit RSA key pair
    -keyout      : where to write the private key
    -out         : where to write the certificate
    -subj        : certificate subject (avoid interactive prompts)

  Alternatively, use mkcert for a locally-trusted CA.

The .key file is the private key and must be kept secret (not in git).
The .crt file is the public certificate, shared with browsers.

In NGINX, reference them with:
  ssl_certificate     /etc/nginx/ssl/login.42.fr.crt;
  ssl_certificate_key /etc/nginx/ssl/login.42.fr.key;

Browsers will show a security warning for self-signed certificates because they
are not signed by a trusted CA. You can add an exception manually.

7. PHP-FPM — FASTCGI PROCESS MANAGER
================================================================================

FastCGI is a protocol for interfacing web servers (NGINX) with external programs
(PHP). It is more efficient than classic CGI because it keeps PHP worker processes
alive rather than spawning a new process for each request.

PHP-FPM is the standard FastCGI implementation for PHP. It manages a pool of
PHP worker processes and routes incoming FastCGI requests to them.

Flow of a PHP request:
  1. Browser requests login.42.fr/wp-login.php over HTTPS
  2. NGINX receives it, decrypts TLS, recognizes .php file
  3. NGINX sends a FastCGI request to wordpress:9000
  4. PHP-FPM receives it, picks a free worker process
  5. The worker executes wp-login.php, generates HTML
  6. PHP-FPM sends the HTML response back to NGINX
  7. NGINX sends it back to the browser over TLS

Key PHP-FPM configuration (/etc/php/x.x/fpm/pool.d/www.conf):
  listen = 0.0.0.0:9000   # Listen on all interfaces, port 9000
  user = www-data          # Run as www-data user
  group = www-data

NGINX fastcgi_params:
  These tell PHP-FPM details about the request. The include fastcgi_params;
  line loads a standard set. The most important additional one is:
    fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
  This tells PHP-FPM which file to execute.

8. ENVIRONMENT VARIABLES AND THE .env FILE
================================================================================

Hardcoding passwords and credentials in Dockerfiles or docker-compose.yml is
a serious security risk (especially if pushed to git).

The solution: use environment variables, stored in a .env file.

The .env file:
  A plain text file with KEY=VALUE pairs. Example:

    DOMAIN_NAME=gcesar-n.42.fr
    DB_NAME=wordpress
    DB_USER=wpuser
    DB_PASSWORD=supersecretpassword
    DB_ROOT_PASSWORD=anothersecret
    WP_ADMIN_USER=gcesar_admin
    WP_ADMIN_PASSWORD=adminpass
    WP_ADMIN_EMAIL=gcesar@student.42.fr
    WP_USER=wpeditor
    WP_USER_PASSWORD=editorpass
    WP_USER_EMAIL=editor@42.fr

Placement: the subject specifies the .env file must be at the root of the srcs/
directory. It should be listed in .gitignore and NEVER committed to git.

Using .env in docker-compose.yml:
  Compose automatically reads .env from the same directory as the compose file.
  Variables are referenced as ${VARIABLE_NAME} in the YAML.

  Alternatively, point a service to it explicitly:
    env_file:
      - .env

Passing variables to containers at build time (ARG):
  If you need a variable during docker build (e.g., to create a db user), pass
  it as a build argument:

    build:
      context: .
      args:
        DB_USER: ${DB_USER}
        DB_PASSWORD: ${DB_PASSWORD}

  Then in the Dockerfile:
    ARG DB_USER
    ARG DB_PASSWORD
    ENV DB_USER=${DB_USER}      # Promote to ENV if needed at runtime

Note on secrets: for production, Docker Secrets is the proper tool. For Inception
(a school project), .env with .gitignore is the accepted approach.

9. PROJECT RULES AND CONSTRAINTS
================================================================================

--------------------------------------------------------------------------------
9.1 MANDATORY RULES
--------------------------------------------------------------------------------

Infrastructure:
  - The entire project must run inside a Virtual Machine
  - All services run in Docker containers
  - Use Docker Compose (through a Makefile) to build and orchestrate
  - Use a single docker-compose.yml file for all services

Images:
  - Write a Dockerfile for EACH service
  - Base images: Alpine or Debian (penultimate stable version) ONLY
  - Do NOT use pre-built images from Docker Hub (no wordpress:latest, etc.)
  - Do NOT use the "latest" tag for base images

Services (mandatory):
  - NGINX container with TLSv1.2 or TLSv1.3 only
  - WordPress + PHP-FPM container (without NGINX inside)
  - MariaDB container (without NGINX inside)

Volumes (mandatory):
  - One volume for the WordPress database (MariaDB data)
  - One volume for the WordPress files
  - Both accessible on the host at /home/login/data/

Network:
  - A docker-network connecting all containers
  - No use of --link, host network, or default bridge network

Security:
  - No passwords or credentials in Dockerfiles
  - Use a .env file for all sensitive variables
  - The .env file goes in srcs/ and must be in .gitignore

Domain:
  - Your domain name must be login.42.fr (replace login with your 42 login)
  - It must point to your VM's local IP in /etc/hosts

WordPress:
  - Must have exactly TWO users: one admin + one regular user
  - The admin username must NOT contain "admin" or "administrator"

Containers:
  - Must NOT crash and restart infinitely (use a proper PID 1 process)
  - Must restart on failure (use restart: unless-stopped or on-failure)

--------------------------------------------------------------------------------
9.2 WHAT IS FORBIDDEN
--------------------------------------------------------------------------------

  - network: host
  - --link flag
  - Pulling pre-built service images (wordpress, nginx, mariadb official images)
  - Using the "latest" tag
  - Running NGINX inside the WordPress or MariaDB container
  - Storing passwords in Dockerfiles or docker-compose.yml directly
  - Running containers as root where not necessary (best practice)
  - Infinite loops (tail -f /dev/null, sleep infinity) as PID 1 instead of the
    actual service process

11. MAKEFILE
================================================================================

The Makefile orchestrates building and running the project. Required targets:

  all:
      @mkdir -p /home/${USER}/data/mariadb /home/${USER}/data/wordpress
      @docker compose -f srcs/docker-compose.yml up -d --build

  down:
      @docker compose -f srcs/docker-compose.yml down

  clean:
      @docker compose -f srcs/docker-compose.yml down
      @docker system prune -f

  fclean: clean
      @docker volume rm $$(docker volume ls -q) 2>/dev/null || true
      @sudo rm -rf /home/${USER}/data

  re: fclean all

  .PHONY: all down clean fclean re

Notes:
  - Always use -f to specify the compose file path
  - Create /home/${USER}/data/ subdirectories before docker compose up, otherwise
    Docker may create them as root and MariaDB/WordPress can't write to them
  - fclean should remove volumes and host data for a clean rebuild

12. HOW THE SERVICES COMMUNICATE (NETWORK FLOW)
================================================================================

1. Browser -> NGINX (port 443, TLS)
   The browser sends an HTTPS request to login.42.fr.
   Your /etc/hosts maps this domain to the VM's IP.
   NGINX handles TLS termination (decrypts the request).

2. NGINX -> WordPress (port 9000, FastCGI)
   For .php files, NGINX forwards the request to wordpress:9000.
   "wordpress" resolves via Docker DNS to the WordPress container's IP.
   The FastCGI protocol carries the request details.

3. WordPress -> MariaDB (port 3306, MySQL protocol)
   WordPress connects to mariadb:3306 using credentials from wp-config.php.
   "mariadb" resolves via Docker DNS to the MariaDB container's IP.
   WordPress reads and writes data (posts, users, options) here.

4. Shared Volume
   WordPress files are on the wp-volume, mounted at /var/www/html in BOTH
   the WordPress container and the NGINX container.
   - WordPress writes/manages its PHP files there
   - NGINX serves static assets (images, CSS, JS) from there directly

Ports summary:
  443  (nginx)     : published to host (reachable from browser)
  9000 (wordpress) : exposed internally only (only nginx can reach it)
  3306 (mariadb)   : exposed internally only (only wordpress can reach it)

13. PID 1 AND THE "daemon off" PROBLEM
================================================================================

PID 1 is the first process started in a Linux system (or container). It has
special responsibilities:
  - It receives SIGTERM when the container is stopped
  - If PID 1 exits, the container exits (all other processes are killed)
  - PID 1 must reap zombie processes (orphaned child processes)

The problem with running services in containers:
  Many server programs (nginx, apache, mariadb, php-fpm) are designed to
  daemonize — they fork into the background and the parent process exits.
  If the parent exits in a container, PID 1 is gone and the container stops.

Solutions:

  NGINX:
    Use "daemon off;" directive. This tells NGINX not to daemonize.
    CMD ["nginx", "-g", "daemon off;"]
    This makes the NGINX process stay in the foreground as PID 1.

  PHP-FPM:
    Use the -F (nodaemonize) flag:
    CMD ["php-fpm8.2", "-F"]
    Or configure daemonize = no in php-fpm.conf.

  MariaDB:
    Start it with mysqld directly in the foreground:
    CMD ["mysqld", "--user=mysql"]
    mysqld does not daemonize by default when run directly.

  General rule: your CMD or ENTRYPOINT must run a foreground process that stays
  alive. If you use a shell script as ENTRYPOINT, end it with:
    exec "$@"      # pass CMD arguments to the script's final command
  or
    exec mysqld --user=mysql
  Using exec replaces the shell with the process, making the process PID 1.

init / tini:
  Some projects use tini (a tiny init system) as PID 1 to handle signal
  forwarding and zombie reaping. This is a bonus-level best practice.
  ENTRYPOINT ["/tini", "--"]
  CMD ["nginx", "-g", "daemon off;"]

14. VOLUMES IN PRACTICE
================================================================================

Bind mount configuration in docker-compose.yml (Inception standard approach):

  volumes:
    db-volume:
      driver: local
      driver_opts:
        type: none
        o: bind
        device: /home/${USER}/data/mariadb

    wp-volume:
      driver: local
      driver_opts:
        type: none
        o: bind
        device: /home/${USER}/data/wordpress

Service mounting:
  mariadb:
    volumes:
      - db-volume:/var/lib/mysql

  wordpress:
    volumes:
      - wp-volume:/var/www/html

  nginx:
    volumes:
      - wp-volume:/var/www/html    # Same volume as wordpress — shared files

What happens if you DON'T mount a volume:
  - MariaDB: database is lost every time the container restarts
  - WordPress: wp-config.php and uploaded media are lost on restart
  - The site would need to be re-installed every time you run make re

Data directory creation:
  The /home/${USER}/data/mariadb and /home/${USER}/data/wordpress directories
  must exist on the host BEFORE docker compose up. Create them in the Makefile.
  If Docker creates them automatically, they are owned by root and MariaDB
  (which runs as mysql user) cannot write to them.

15. THE /etc/hosts ENTRY (login.42.fr)
================================================================================

Since login.42.fr is not a real public domain (your site is local), the browser
needs to be told that login.42.fr points to your VM's IP address.

Add this line to /etc/hosts on the machine where you open the browser
(usually the VM itself if you're testing locally):

  127.0.0.1    gcesar-n.42.fr

Or with the VM's actual IP if testing from another machine:
  192.168.X.X  gcesar-n.42.fr

After this, opening https://gcesar-n.42.fr in the browser reaches NGINX on port
443 of your VM.

The evaluator will check that your domain follows the pattern login.42.fr.

--------------------------------------------------------------------------------
16.1 REDIS CACHE
--------------------------------------------------------------------------------

Redis is an in-memory data store. Used as an object cache for WordPress: instead
of querying MariaDB for every page load, WordPress stores computed results in
Redis and retrieves them instantly.

How it works with WordPress:
  1. Run a Redis container (based on Alpine, install redis)
  2. Install the Redis Object Cache WordPress plugin (via WP-CLI)
  3. Configure wp-config.php to use Redis:
       define('WP_REDIS_HOST', 'redis');
       define('WP_REDIS_PORT', 6379);
  4. Enable the plugin: wp plugin activate redis-cache && wp redis enable

Redis port: 6379 (only exposed internally to wordpress container)
No password required for local dev, but can add requirepass in redis.conf.

--------------------------------------------------------------------------------
16.2 FTP SERVER
--------------------------------------------------------------------------------

An FTP (File Transfer Protocol) server allows transferring files to/from the
WordPress volume, useful for managing media uploads.

Common FTP server for this purpose: vsftpd (Very Secure FTP Daemon)

Configuration points:
  - Passive mode ports: 21 (control) + a range for data (e.g., 21100-21110)
  - Point the FTP root to /var/www/html (the wp-volume)
  - Create an FTP user with access to that directory
  - Configure vsftpd.conf:
      local_enable=YES
      write_enable=YES
      local_root=/var/www/html
      pasv_enable=YES
      pasv_min_port=21100
      pasv_max_port=21110

Testing: connect with FileZilla or the ftp command to login.42.fr on port 21.

16.3 STATIC WEBSITE

Typically a small HTML/CSS/JS portfolio or landing page, served on another port
(e.g., 80) via its own NGINX or lighttpd instance.

16.4 ADMINER

Adminer is a lightweight database management web UI (alternative to phpMyAdmin).
Served as a PHP application, it lets you browse the MariaDB database through

Setup:

  - Download adminer.php into the web root
  - Route a port on NGINX to the Adminer container

Connect Adminer to MariaDB using the service name "mariadb" as the host.

17. COMMON MISTAKES AND HOW TO AVOID THEM
================================================================================

1. Container exits immediately after start
   Cause: the main process daemonizes or exits.
   Fix: ensure CMD runs a foreground process (use "daemon off;", -F flags, exec).

2. WordPress can't connect to MariaDB
   Cause: MariaDB isn't fully initialized when WordPress starts.
   Fix: add a retry loop in the WordPress entrypoint:
     until mysqladmin ping -h mariadb --silent; do sleep 2; done

3. Permission denied on /var/lib/mysql or /var/www/html
   Cause: volume directory created by root, but container runs as mysql/www-data.
   Fix: create the host directories before docker compose up in the Makefile,
   and/or chown them in the entrypoint script.

4. NGINX shows "502 Bad Gateway"
   Cause: WordPress container (PHP-FPM) not running or not reachable on port 9000.
   Fix: check WordPress container logs, verify it's on the same network, confirm
   fastcgi_pass uses the correct service name and port.

5. TLS errors in browser
   Cause: self-signed cert is not trusted. This is expected.
   Fix: add a browser exception (Advanced -> Proceed). If you used mkcert, trust
   the local CA in your browser/OS.

6. Passwords visible in git history
   Cause: .env file committed, or credentials hardcoded in Dockerfile.
   Fix: add .env to .gitignore immediately. If you accidentally committed
   credentials, rotate them and rewrite git history.

7. "exec format error" or scripts fail on start
   Cause: shell script has Windows line endings (\r\n) instead of Unix (\n).
   Fix: run dos2unix on your scripts, or configure git:
     git config --global core.autocrlf input

8. depends_on doesn't wait for MariaDB to be ready
   Cause: depends_on only waits for the container to start, not the service
   inside to be ready.
   Fix: use a health check loop in the WordPress entrypoint as described above.

9. Volume data not persisted between make re runs
   Cause: volumes are removed by fclean or docker system prune -v.
   Fix: this is expected for fclean. For normal re-starts without fclean, data
   should persist on the bind-mounted host directory.

10. NGINX 403 Forbidden or blank page
    Cause: WordPress files not in /var/www/html, or wrong root in nginx.conf.
    Fix: verify the wp-volume is mounted at /var/www/html in BOTH containers,
    and that WordPress files exist there (docker exec + ls -la).

18. USEFUL CONCEPTS FOR THE DEFENSE (EVALUATION)
================================================================================

The evaluator will ask conceptual questions. Be ready for:

Q: What is Docker? What is the difference between a container and a VM?
A: Docker packages apps in containers that share the host kernel, while VMs
   emulate full hardware and run separate kernels. Containers are lighter and
   faster; VMs offer stronger isolation.

Q: What is a Dockerfile?
A: A text file with instructions to build a Docker image. Each instruction
   creates a layer. The result is an image used to create containers.

Q: What is PID 1 and why does it matter in containers?
A: PID 1 is the first process in a container. When it exits, the container stops.
   Services that daemonize must be configured to run in the foreground.

Q: Why can't you use pre-built images?
A: The subject forbids it to ensure you understand how each service is configured
   and installed from scratch.

Q: What is TLS and why use only 1.2 or 1.3?
A: TLS encrypts traffic. TLS 1.0 and 1.1 have known vulnerabilities and are
   deprecated. 1.2 and 1.3 are current secure standards.

Q: What are volumes and why are they used?
A: Volumes persist data outside the container's writable layer so data survives
   container restarts and removals.

Q: What is the purpose of the .env file?
A: To store sensitive credentials separately from code, avoiding secrets in
   Dockerfiles or docker-compose.yml (which could be committed to git).

Q: What is Docker Compose and why use it?
A: A tool to define and run multi-container applications with a single YAML file.
   It simplifies orchestration and allows services to share networks and volumes.

Q: What is PHP-FPM and what role does it play?
A: PHP-FPM is a FastCGI process manager that runs PHP code. NGINX itself cannot
   execute PHP, so it delegates PHP requests to PHP-FPM via the FastCGI protocol.

Q: What is the network in Docker Compose?
A: A user-defined bridge network allowing containers to communicate by service
   name. Only the NGINX container exposes a port to the host (443).

Q: How does WordPress communicate with MariaDB?
A: WordPress connects to mariadb:3306 using the MySQL protocol. Docker DNS
   resolves "mariadb" to the MariaDB container's IP.

Q: What would happen if you removed the volumes?
A: All database data and WordPress files would be lost. The site would reset
   to a blank state on the next docker compose up.

19. GLOSSARY
================================================================================

Alpine Linux    : A minimal Linux distribution (~5MB). Common base for Docker
                  images due to its small size.

ARG             : Dockerfile build-time variable. Available during docker build,
                  not at container runtime (unless promoted to ENV).

Bridge network  : Default Docker network mode using a virtual switch. Containers
                  on the same bridge can communicate.

cgroups         : Linux kernel feature to limit and account for resource usage
                  (CPU, memory) of process groups.

CMD             : Dockerfile instruction for the default command to run at
                  container start. Can be overridden by docker run.

Container       : A running instance of a Docker image. Isolated process(es)
                  with their own filesystem, network, and process namespace.

Daemonize       : When a process forks itself into the background and the parent
                  exits. Bad in containers — prevents PID 1 from staying alive.

Debian          : A stable Linux distribution. Common base for Docker images when
                  a full-featured OS is needed.

Docker          : Platform for building and running containerized applications.

Docker Compose  : Tool for defining and running multi-container Docker apps via
                  a YAML configuration file.

Docker Hub      : Public registry for Docker images. Source of official images.

Dockerfile      : Text file with instructions to build a Docker image.

ENV             : Dockerfile instruction to set environment variables available
                  at runtime inside the container.

ENTRYPOINT      : Dockerfile instruction for the command that always runs. CMD
                  provides default arguments to it.

exec form       : JSON array syntax for CMD/ENTRYPOINT: ["cmd", "arg1"]. Makes
                  the process PID 1 directly, without a shell wrapper.

expose          : Dockerfile/Compose directive to document a container's port.
                  Does NOT publish it to the host. (Use ports: for that.)

FastCGI         : Protocol for web servers to communicate with external processes
                  (like PHP-FPM). More efficient than classic CGI.

FTP             : File Transfer Protocol. Used to upload/download files.

image           : Read-only layered template for creating containers.

layer           : A filesystem snapshot created by each Dockerfile instruction.
                  Layers are cached and reused.

MariaDB         : Open-source relational database, MySQL-compatible. Used by
                  WordPress for data storage.

namespace       : Linux kernel feature for isolating process views of system
                  resources (PID, network, filesystem, etc.).

NGINX           : High-performance web server and reverse proxy.

PID 1           : The first process in a Linux system or container. Its exit
                  causes all other processes to be killed.

PHP-FPM         : PHP FastCGI Process Manager. Runs PHP scripts for NGINX.

ports           : Compose directive to publish a container port to the host.
                  Format: "host_port:container_port"

restart         : Compose directive defining container restart behavior.

reverse proxy   : A server that forwards client requests to backend services.
                  NGINX acts as a reverse proxy for WordPress.

self-signed cert: A TLS certificate signed by its own private key rather than
                  a trusted CA. Used for local development.

shell form      : Non-JSON syntax for CMD: CMD nginx. Wraps command in /bin/sh -c,
                  making sh the PID 1 process (not ideal for signal handling).

TLS             : Transport Layer Security. Protocol for encrypted communications.
                  Used for HTTPS.

volume          : Docker mechanism for persisting data outside of a container's
                  writable layer.

WP-CLI          : Command-line tool for managing WordPress installations without
                  a browser.

WordPress       : Popular open-source CMS (Content Management System).

.env file       : Plain text file of KEY=VALUE pairs for environment variables.
                  Loaded by Docker Compose automatically.
